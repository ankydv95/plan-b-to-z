Community Section — 3 Approaches

Same features, different architecture and build complexity

A

Single-table, flat posts

One community_posts table with a nullable cohort_id column. Posts with no cohort_id appear in the global feed. Posts with a cohort_id appear inside that group.

Pros

  • Simplest DB schema
  • Easiest queries
  • Fastest to build

Cons

  • Replies/threading needs a parent_id
  • Reactions need a separate table
  • Hard to add cohort-specific pinned resources later

Build time: ~2–3 days

B

Posts + Cohort Groups (recommended)

Two core tables: community_posts (global feed + cohort feed) and community_groups (one row per career path cohort). Users join groups via community_group_members. Resources pulled from existing career_paths data — no new table needed.

Pros

  • Clean separation of global vs cohort
  • Groups table enables member directory easily
  • Resources reuse existing career path DB
  • Extensible for v2 features

Cons

  • More tables to set up with RLS
  • Slightly more complex queries

Build time: ~4–5 days

C

Full social graph

Posts, replies, reactions, follows, notifications, real-time via Supabase Realtime subscriptions, read receipts. Everything you'd expect from a proper social platform.

Pros

  • Best long-term experience
  • Real engagement metrics

Cons

  • 2–3 weeks to build properly
  • Complex RLS policies
  • Realtime adds infra complexity
  • Overkill for v1 — community needs content first

Build time: ~2–3 weeks

My recommendation: B. It's the right level of structure — not a hacky single table, not an over-engineered social graph. Groups map cleanly to career paths already in the DB. The member directory falls out naturally. Resources are free to add (reuse career_paths data). And the max-5-groups constraint is easy to enforce at the DB level.
